# 文件署名与贡献记录规范

版本：1.0
日期：2026-09-01

## 为什么要署名

项目文件需要能看出“谁负责、谁具体做了什么、谁审核过”。Git提交账号只能说明谁执行了提交，不能代替真实贡献记录；使用AI整理的文件也不能只写AI而省略提出问题和做技术判断的人。

## 文档署名格式

新建或大改Markdown、报告、PPT说明和实验报告时，在标题后写：

```text
项目组：周航正、霍奕茗、于跃、叶安、王健祺
文件负责人：姓名
主要撰写：姓名
技术贡献：姓名（具体内容）；姓名（具体内容）
审核：姓名 / 待项目组审核 / 待指导教师确认
AI协助：无 / Codex（整理、校对、代码辅助等）
```

规则：

1. 只记录实际贡献，不默认把全体成员写成共同作者。
2. 项目组名单可以完整保留；“技术贡献”必须写到具体内容。
3. 未审核的文件明确写“待审核”，不能因为已经上传就写成已通过。
4. AI只能列为协助工具，需求提出、技术判断和最终责任仍归项目成员。
5. 修改别人负责的文件时保留原署名，并在贡献记录中追加本次修改人和内容。

## 代码和Simulink文件怎样署名

- 不要求在每个函数顶部堆叠长名单；代码作者和贡献内容统一记录在对应模块的 `README.md`。
- 模块README至少包含“负责人、贡献者、主要文件/功能、日期”四列。
- `.slx`文件要在同目录README或接口文档中记录当前负责人和本次结构修改人。
- 自动生成文件不手工加署名，在生成脚本和同目录README中说明来源。

推荐表格：

```text
| 姓名 | 角色 | 主要文件/功能 | 日期 |
|---|---|---|---|
| 张三 | 模块负责人 | 功率模型、参数标定 | 2026-09-01 |
```

## 提交和上传要求

1. 上传前检查新增文档是否有署名区，模块README是否更新贡献表。
2. Git提交信息说明本次改了什么；工作日志记录本次实际参与人。
3. 一次提交包含多人工作时，在工作日志中分别写出贡献，不用一句“全体完成”代替。
4. 无法确认作者时先写“待确认”，不得猜测姓名。
5. 署名错误应单独修正并说明原因，不重写历史来隐藏错误。
