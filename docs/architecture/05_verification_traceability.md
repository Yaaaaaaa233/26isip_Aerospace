# 需求、MoE/MoP与验证追溯

版本：0.1
日期：2026-09-01
状态：建议基线

## 先看结论

- **MoE**看任务结果，例如“续航是否提高、任务是否安全完成”。
- **MoP**看过程表现，例如“平均功率多大、速度误差多大、触发了几次回退”。
- 最终不能只放一张功率下降图，需要同时证明任务完成、轨迹没坏、安全约束没被违反。
- 目前仓库主要是代理对象和未校准平台证据，所以可以说“算法和闭环能运行”，还不能说“真实无人机节能多少”。

## 1. 这份表有什么用

这份表告诉大家：每个项目目标应该看什么指标、需要记录什么数据、在哪个场景测试。这样汇报时可以从目标一路找到结果，不会只剩几张算法曲线。

## 2. 证据等级

| 等级 | 数据来源 | 可支持的结论 |
|---|---|---|
| E0 | 静态/动态代理对象 | 算法因果性、接口和数值行为 |
| E1 | 未校准六自由度/平台估算 | 闭环、状态机、约束和回归行为 |
| E2 | 由独立数据校准并留出验证集的仿真 | 指定模型适用范围内的能耗比较 |
| E3 | SITL/HITL或真实日志回放 | 接口、时序和已记录工况的复现 |
| E4 | 台架/受控飞行实测 | 对应试验边界内的真实系统结论 |

任何报告必须给出证据等级。较低等级不能越级支持真实节能或飞行安全结论。

## 3. 顶层需求

| ID | 需求 | 验证方法 |
|---|---|---|
| R-MIS-01 | 在选定盘旋/巡航任务中降低平均电功率并提高估算续航 | 配对场景仿真、校准后复验 |
| R-MIS-02 | 完成规定轨迹和时长，不通过停飞或破坏任务来降功率 | 轨迹、速度和任务完成检查 |
| R-SAF-01 | 优化不得造成姿态、高度、偏航和执行器硬约束违规 | 约束总线与故障注入 |

| R-ROB-01 | 噪声、延迟、风变化和数据缺测下行为有界并可回退 | 多种子Harness和故障测试 |

## 4. MoE：任务级效能度量

| ID | 名称 | 定义 | 适用任务 |
|---|---|---|---|
| MoE-01 | 安全任务完成率 | 满足时长/路径且零硬违规的场景数/总场景数 | 全部 |
| MoE-02 | 续航提升率 | `(T_est_policy-T_est_base)/T_est_base*100%` | 固定时长盘旋/等待 |
| MoE-03 | 配对节能率 | `(E_base-E_policy)/E_base*100%`，相同时间窗 | 固定时长任务 |
| MoE-04 | 未见场景胜出率 | 策略功率不高于基线且任务完成的未见种子比例 | 不规则风 |
| MoE-05 | 最差场景退化 | 所有测试场景中相对基线的最大不利变化 | 鲁棒性评价 |

当前主任务建议以MoE-01、MoE-02和MoE-04为核心。若任务改为固定航程，应新增以完成航程总能量为核心的MoE，而不是沿用平均功率口径。

## 5. MoP：系统性能度量

| ID | 名称 | 单位/公式 | 主要信号 |
|---|---|---|---|
| MoP-01 | 平均功率 | `mean(P)` W | `power_w` |
| MoP-02 | 累计能量 | `trapz(t,P)` J | `time_s,power_w` |
| MoP-03 | 速度跟踪RMSE | m/s | 实际/参考切向速度 |
| MoP-04 | 径向/横向误差RMSE与最大值 | m | 位置、路径定义 |
| MoP-05 | 高度误差RMSE与最大值 | m | `altitude_m` |
| MoP-06 | 姿态/偏航偏差 | rad、rad/s | 姿态、角速度 |
| MoP-07 | 收敛/重新适应时间 | s | 参考、功率、场景事件 |
| MoP-08 | 稳态参考振荡 | m/s或无量纲 | `v_ref/eta_ref` |
| MoP-09 | 执行器利用率/饱和次数 | %、次 | PWM/RPM和约束标志 |
| MoP-10 | 安全动作 | 冻结/回退次数及持续时间 | 状态、原因码 |
| MoP-11 | 无效数据比例/数据年龄 | %、s | valid、sample time |
| MoP-12 | 动作阻止比例 | 被门控修改的决策数/总决策数 | 候选/施加命令 |

每个指标实现必须保存公式版本、统计窗口和缺失值处理规则。

## 7. 进入下一步前要检查什么

### Gate A：问题和接口冻结

- 指导教师确认主任务是续航、固定航程或最大航程之一。
- `ScenarioConfig/WindSample/PlaneState/ControlCommand/EvaluationRecord`冻结为1.0。
- 至少一个Mock端到端场景可运行并生成指标。

### Gate B：物理与平台可信

- 功率模型来源、适用范围和校准/留出验证误差可追溯。
- 平台明确世界风、空速和地速关系。
- M2控制分配器满足总推力、关键力矩、偏航和饱和约束。

### Gate C：单变量与场景基线

- 速度和转速比单变量策略分别与固定基线配对。
- 圆周正弦风场景有解析/离线参考和一致评价窗。
- Harness能一键重放场景矩阵。

### Gate D：协同优化

- 交替优化不出现持续振荡或互相覆盖。
- 结果不差于两个单变量基线，且零硬约束违规。

### Gate RL：正式强化学习

采用 [`ADR-002-rl-readiness.md`](../decisions/ADR-002-rl-readiness.md) 的全部条件。未通过前，RL仅作为接口预研，不进入最终主结论。

## 9. 验收结果最小记录

每次正式验收至少保存：

```text
requirement_id
scenario_id
baseline_id
policy_id
git_revision
model_revision
random_seed
metric_id, value, unit, window
constraint_violations
evidence_level
verdict
evidence_path
```

判定只能是 `pass`、`fail` 或 `inconclusive`。数据源不可信或任务口径不一致时使用 `inconclusive`，不能为得到“通过”而放宽约束或更换随机种子。
